# O2A deployment and recovery readiness

O2A examines repository code, hosted CI and a disposable synthetic rehearsal. Production deployment, IAM, TLS termination, firewall controls, alert delivery and recovery objectives have no operational acceptance evidence. Owners below are proposed roles and remain unassigned unless the organization records an appointment.

## Proposed network and secret boundaries

Expose only the TLS web entry point and its approved API paths. Route candidate and institution traffic through the same-origin web rewrite. Restrict the Control Centre to an approved administrative access boundary as well as application RBAC. Route API, AI and worker processes through private service discovery and firewall policy. PostgreSQL and Redis have no public listeners in the proposed design. Reach storage only through its guarded frontend. Restrict the Console to operators and never route backend S3 or Console ports to clients. Allow outbound provider traffic only for the worker and identity with separately approved provider authority.

Use a managed secret store and separate application, migration, worker, storage, recovery and operator identities. Keep server-only credentials out of public Next variables and browser responses. Scope bucket permissions to approved resources and segregate delete and administration privileges. Require secure cookies, verified TLS for applicable links and a dedicated rotation/revocation procedure. The synthetic harness uses temporary processes and credentials scoped to its own containers. Its disposable MinIO root credential bootstraps and exercises the test bucket, so it is not evidence for production credential separation. The development Compose publishes PostgreSQL and Redis without a loopback qualifier and uses development-only credentials. Neither development Compose file is a production deployment specification.

Network/firewall behavior outside the disposable guard proof, ingress TLS, service account isolation, secret injection and rotation are **NOT VERIFIED**. AWS O1B.4 remains a separate gate. AWS smoke **NOT RUN**, AWS operational compatibility **NOT VERIFIED**, production storage provider **NOT SELECTED**. A managed replacement changes egress and DNS, server identity and bucket policy, key custody, replication and versioned restores, provider-side audit, retention and processor review. Transcription's current CLI requires the `s3` backend setting. The O1B.3 trial mode is a compatibility harness, with no worker deployment acceptance.

## Reproducible acceptance and limits

The supply-chain job runs `python scripts/storage-readiness/operations.py "$RUNNER_TEMP/o1a-containers"` after the existing O1B.2 guard rehearsal. It selects the exact scanned MinIO and decoder image identities and uses the pinned CI PostgreSQL and Redis images. It creates new, randomly named, labelled Docker resources. It runs the real API and AI subprocesses and the three worker entrypoints. It writes only redacted counts, statuses and hashes to `operations-readiness.json`. The application workflow covers forced worker process termination during actual synthetic execution, heartbeat renewal, stale-lease fencing, restart, bounded retry, duplicate completion, cancellation and stale evidence. The browser runner stops its own API process, holds the outage for a bounded interval and verifies the user-visible error and recovered sign-in.

Local reproduction requires an explicitly dedicated Docker profile and the repository API dev dependencies. With that profile selected explicitly, build the guarded storage and decoder images using `infra/minio-source.Dockerfile` and `infra/media-probe.Dockerfile`. Run:

```sh
PRUFAI_DISPOSABLE_OPERATIONS_TEST=1 python scripts/storage-readiness/operations.py \
  /tmp/prufai-o2a-evidence --local-image <guarded-image> --local-decoder <decoder-image>
```

The rehearsal compares row counts and deterministic snapshots across organizations, attempts, response revisions, media bindings, scoring runs, result versions and releases, privacy grants/cases/scopes, Standards references and audit. It restores PostgreSQL and current synthetic objects to distinct volumes, then verifies authenticated Range, exact Standards reads, tenant denial and release confidentiality. The archive uses owner-only temporary plaintext files and disappears after verification. Historical S3 versions and delete markers, encryption, simultaneous outages, point-in-time recovery, RTO and RPO require independent proof. A PostgreSQL outage currently returns a generic HTTP 500 on login while `/health` stays 200. Preserve that distinction in dashboards and preflight. Redis and guarded media failures return bounded safe error responses in the synthetic checks.

## Operational telemetry and alert routing

Emit aggregate measurements by bounded service, route template, operation type, status class and failure category. Correlate with generated request IDs and approved audit references in restricted traces. Avoid tenant, candidate, object, credential and presign labels. Never ingest raw path parameters, payloads, transcripts, recordings, responses, answer keys, private rationale or secrets. Audit records are governance evidence. Derive operational views without writing or rewriting audit history.

| Signal and candidate source | Severity and action | Intended responder and runbook | Threshold or delivery |
| --- | --- | --- | --- |
| API/proxy response classes, liveness, authenticated dependency probes | Page on sustained candidate workflow failure or database unavailability | Application and database operations, **Database outage** | Baseline and thresholds pending |
| Authentication failures and Redis unavailability, `auth.login.failed` and auth 503 | Investigate sustained failures or failure to enforce throttling | Identity operations, **Service startup / database outage** | Baseline pending |
| Queue age/depth by worker/status, retry exhaustion and expired leases from persisted jobs | Investigate sustained backlog or failure to recover. Escalate exhaustion when evidence is blocked | Worker operations, **Worker restart / stale worker recovery** | Baseline and job SLO pending |
| Guarded readiness, unsigned-trailer denial marker, direct backend reachability | Treat reachable backend as a security incident. Distinguish a denied probe from unexpected bypass | Storage and security, **Storage guard failure** | Any verified unguarded backend path is urgent. Rate baseline pending. |
| Object length or SHA mismatch, media validation and decoder failures | Freeze affected evidence actions on integrity mismatch. Triage decoder outage separately | Storage and media operations, **Object integrity incident** | Any verified authoritative mismatch is urgent. Rate baseline pending. |
| Evaluation failure category and result release denial/error | Separate workflow failure from unauthorized mutation. Escalate unauthorized disclosure immediately | Evaluation and assessment operations, **Result-release confidentiality incident** | Baseline pending |
| Privacy authorization denial and scoped audit | Investigate unusual denial patterns and confirmed exposure | Privacy and security, **Privacy incident escalation** | Baseline and privacy policy pending |
| Backup checksum or age failure, restore reconciliation failure | Stop cutover or recovery acceptance. Investigate without erasing evidence | Database and storage operations, **Backup and restore** | Retention, RPO/RTO and thresholds require approval |

Monitoring is **PARTIAL**. The signal sources and synthetic failures are observable, and production aggregation and retention are unverified. Paging and notification destinations are **NOT CONFIGURED**.

## Runbooks

Before using any command, identify the environment, exact owned process or labelled container, database name and revision, approved storage endpoint, backup custody and authorized operator. Commands below are for the approved isolated or separately reviewed target only. Escalation roles are proposed and require an actual appointment.

| Trigger | Supported operation and verification | Escalation or recovery condition |
| --- | --- | --- |
| Deployment preflight | Inspect the clean commit and CI evidence, validate the Compose model with `docker compose -f <approved-file> config --quiet`, verify exact database identity and run `python -m alembic heads` from `services/api`. Verify `pg_isready`, authenticated PostgreSQL, Redis PING, guarded readiness and authenticated canary. | Platform operator signs off only on the exact target. A stale or multi-head migration, occupied port or unresolved network policy stops launch. |
| Service startup | For approved local dev only, `make infra-up` selects the generic Compose. For an owned synthetic or separately approved target, start its PostgreSQL, Redis and guarded MinIO, then run `python -m alembic upgrade head` once from `services/api` against the verified DSN. Launch API with `python -m uvicorn app.main:app --app-dir services/api --host 127.0.0.1 --port 8000`, AI with `--app-dir services/ai --port 8001`, and web with `npm run start --prefix apps/web -- --hostname 127.0.0.1` after build with the intended API URL. Start workers after checking authorization. | Probe both `/health` routes and web `/login`, then verify a scoped canary. Production process supervision and routing are unverified. |
| Service shutdown | Drain entry traffic. Send SIGTERM to owned workers first, then to API, web and AI processes after current work drains. Stop only the approved Compose project with `docker compose -p <owned-project> -f <approved-file> stop`. | Verify process exit and that labelled volumes remain present. Preserve queued jobs and authoritative evidence. |
| Worker restart or stale lease | Review job state and lease deadline, terminate only the owned consumer, then relaunch `python -m app.speech_transcription.worker`, `python -m app.writing_execution.worker` or `python -m app.speaking_execution.worker` from the API environment. `--once` is a diagnostic for a specifically approved synthetic queue. | Observe eligible reclaim and one fenced completion. Never rewrite lease, status, scores or provider artifacts to force success. |
| Database or auth dependency outage | Inspect the intended server and `pg_isready`, authenticated `SELECT 1`, Alembic head and Redis PING as applicable. Drain writes and review last known commit and dependency state. | Reopen after authorized requests succeed and history checks reconcile. A process liveness 200 does not clear the incident. |
| Storage guard failure | Verify exact guarded container identity and its frontend readiness. Test that both backend ports deny unprivileged reachability before restarting the owned container. | Do not route around the guard. Recover after a private canary read, Range and the denial probe succeed. |
| Object integrity incident | Suspend release or assessment for affected evidence, verify pinned SHA and reference through the authorized service, and retain the exact original versions and restricted audit. | Storage and security review. Recover from a verified copy with authorized reconciliation and lineage preservation. |
| Backup and restore | Rehearse with `scripts/storage-readiness/operations.py`. An approved operator can use `pg_dump -Fc --no-owner --no-privileges` for the verified source and `pg_restore --exit-on-error --no-owner --no-privileges` to a separate approved empty target. Pair the database recovery point with a private object manifest and SHA-256 verification. | Confirm counts, content types, references, tenant access and result confidentiality. Production encryption, version retention and restore ownership remain unverified. |
| Failed migration | Record the exact failed revision, stop new traffic, verify `python -m alembic current` on the approved target and inspect the migration's transactional state. Rehearse the remedy on a restore before retry. | No blind downgrade, stamp, or live restore. Database owner must approve recovery and verify exact history. |
| Privacy incident or result-release confidentiality incident | Pause the affected access or release route using existing authority and operator controls. Preserve redacted audit, exact result/evidence versions and request references. Inspect authorized Control Centre and institution views, and confirm revocation visibility from a separate test identity. | Escalate to assigned privacy, security and assessment owners. Preserve evidence and follow approved incident policy. No ad hoc deletion or publication. |
