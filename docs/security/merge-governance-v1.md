## Normal merge policy

1. Submit a pull request to `main`. Require one current GitHub approval from a write-authorized human who did not author or implement the change and can withhold approval. Record the review against the exact head and assess the effect of the current base. Keep auto-merge off.
2. Require fresh approval after changes to the reviewed diff, plus approval of the most recent reviewable push by someone other than its pusher. Resolve review conversations and all blocking changes requests. Dismissal is exceptional. Preserve the original review, record the reason and authority, and obtain a replacement independent review before merging. GitHub's blocking semantics depend on reviewer permissions. The operator policy covers workarounds such as using another account or dismissing unresolved findings. [GitHub ruleset review controls](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging)
3. Require all five [verified Actions checks](github-ruleset-operator-plan.md#required-check-contexts) on the current revision. The operator must confirm successful execution of the required tests and evidence steps for security-sensitive changes. Future workflow changes affecting check coverage, skips, artifacts, service execution, or sourcing require security review.
4. For changes to authentication, tenant/role boundaries, assessment confidentiality, privacy, storage, deployment or CI trust, additionally obtain a qualified independent security review tied to the exact SHA. This is a proposed human control. GitHub has no named security reviewer configured here. An ordinary approval or account attribution does not establish expertise or organizational independence. Reviewers submit decisions personally. AI tools can prepare evidence.
5. The owner designates a qualified human in writing before granting any collaborator access. Record GitHub identity, review scope, organizational authority, separation from implementation, start/end or review date, and revocation owner. With no eligible independent collaborator, normal merges wait. Retrospective PR #60 evidence can be reviewed without write access using the public diff and an authenticated, authorized decision record.

## Emergency exception proposal

The normal ruleset has an empty bypass list. An urgent incident with material impact may justify requesting an exception from a separately authorized human emergency approver. A scheduling problem or absent routine reviewer provides no emergency basis.

- Record the incident, exact PR/head and base, affected control, potential harm of waiting and bypassing, rollback plan, and proposed scope and expiration. Identify both authorizing and executing humans. Preserve CI and review failures in the record.
- Prefer the normal reviewed PR route. If the owner expressly approves an emergency configuration change and the repository supports it, use an audited, time-limited PR-only exception for the authorized human. Verify actual support before use. A ruleset actor grant is broader than a SHA, so freeze other merges and record the approved exact SHA separately. Keep force-push and deletion restrictions in force. Avoid an always-on actor, unchecked exemption, direct push, or bot bypass. If the platform cannot enforce the approved boundary, keep the normal gate and escalate.
- Capture actual authorization, before/after settings, actor, time, rule or timeline event, check results, and final commit. Revoke temporary access and verify the restored controls immediately. If a check remains failed, record the unresolved risk.
- Commission independent post-event review on the exact diff and incident evidence, track corrective work, and record a dated closure or leave the exception open. This prospective process does not dispose of the [historical exceptions](review-exception-ledger.md).
