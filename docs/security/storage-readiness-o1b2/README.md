# O1B.2 guarded object storage rehearsal

This rehearsal tests containment and recovery for disposable PrüfAI storage. It does not patch the community MinIO executable or establish production storage safety. CVE-2026-40344 and CVE-2026-41145 remain **PRESENT_CONTAINED only in the topology for which the rehearsal passes**. The boundary excludes Docker administrators, users with execution or network-namespace access inside the storage container, unguarded entrypoints, and other networks and deployments.

The baseline is PR #52's merge `d0bfdf7b7c828f11c4d2a9f0a7e7261f06730058`: [application CI](https://github.com/moaltamimi-unbiasedtalent/PrufAI/actions/runs/42567102847), [scanner acquisition failure, attempt 1](https://github.com/moaltamimi-unbiasedtalent/PrufAI/actions/runs/42567102826/attempts/1), [verified failed-job rerun, attempt 2](https://github.com/moaltamimi-unbiasedtalent/PrufAI/actions/runs/42567102826/attempts/2). The verified attempt 2 container archive, artifact `13653129128`, had SHA-256 `a123d1e62783a4150090c0b13afdff9d77f4a6a3387a127b3836b6005426bcd6`. See [O1A inventory](../supply-chain-o1a/README.md) and [O1B.1 evidence](../storage-decoder-o1b1/README.md) for the original scope and open findings.

## Run and read the proof

The supply-chain workflow builds and scans the exact Linux amd64 image, runs the existing MinIO and audio checks, and then runs `python scripts/storage-readiness/check.py "$RUNNER_TEMP/o1a-containers"`. The new step does not change scanner installation, severity policy, original checks, or the application suite. It fails when a required assertion fails. Inspect `storage-readiness.json` in the container/Go evidence artifact and verify that its checkout SHA equals the PR head. Archive checksum, per-image identities and CycloneDX SBOMs, Go build metadata, binary hashes, scanner provenance and full findings accompany the report. A missing or incomplete report does not establish containment. The app's required PostgreSQL, Redis, MinIO, and browser reports are separate evidence.

For a local rehearsal, explicitly select a **disposable** Docker context with IPv6 enabled, no operational workloads, and permission to inspect both bridge and engine-host paths. From the checkout with the existing API development dependencies installed in an isolated Python environment:

```sh
docker build -f infra/minio-source.Dockerfile -t prufai-o1b2-minio:local infra
PRUFAI_DISPOSABLE_STORAGE_TEST=1 python scripts/storage-readiness/check.py \
  /tmp/prufai-o1b2-evidence --local-image prufai-o1b2-minio:local
```

The rehearsal generates names, labels and credentials; it validates ownership and database names and cleans up only those resources. Source and restore each have distinct named storage and database volumes; no existing volume or local database is mounted. On a Docker Desktop or Colima VM, engine-host IPv6 and bridge tests are VM-side, and loopback IPv4 is also tested from the Python process running the rehearsal. A local arm64 build is supplemental and does not inherit amd64 scan identity. The probe-only Python base is digest pinned in the harness; the SDK closure comes from the existing API environment. The probe image is separate from the deployment-image SBOM inventory.

| Path | Required evidence |
| --- | --- |
| S3 frontend `9000` and Console frontend `9001` | Guard wildcard IPv6 listener in the storage namespace; IPv4 and IPv6 bridge peers reach the guard. Both published ports are loopback only, and the Console responds on its guarded port. |
| S3 backend `19000` and Console backend `19001` | Loopback listeners only inside storage namespace; no backend publication. Unprivileged same-bridge and separate-bridge peers and engine-host IPv4/IPv6 routing cannot connect directly. |

| Unsafe write paths | Mixed case, whitespace, repeated/conflicting and combined values, malformed syntax, multipart, Snowball and query-credential probes. The guard denial marker or parser failure is required; unchanged keys, current versions and original hashes are checked independently. |
| Failure and recovery | SIGKILL, SIGTERM, container stop, backend pause, backend SIGKILL, start and bridge recreation. Probe both frontend and backend paths while unavailable, prove signed client failure, a bounded SDK retry and reissued operation after recovery, and recheck object integrity. |

## Restore contract and cutover boundary

The test creates two `ORIGINAL_SYNTHETIC` Standards references using the real registry service, independent fixture review identities, Alembic migrations and PostgreSQL. It validates exact bytes, SHA-256, size, MIME type, ownership/classification and application reference. It takes a `pg_dump -Fc` plus the current private objects and checksum manifest and restores into a second empty PostgreSQL and guarded MinIO environment. The database archive restores exact logical references. The new bucket creates new physical version IDs and the evidence maps those to the original IDs. It does not back up historical S3 versions or unfinished multipart uploads. The plaintext backup is synthetic only, with directory mode `0700` and file mode `0600`, and is deleted at the end. No encrypted backup, point-in-time recovery, RTO or RPO is proven. Only summary metadata and checksums are retained as CI evidence, not the backup or fixture object bodies.

The restore is accepted only if the real registry can verify the exact restored object and unauthorized access stays denied. The rehearsal tests incomplete and corrupt archives, unavailable storage, bad credentials, absent objects, checksum and provenance faults, orphaned objects and a mismatched archive reference. It also proves the database trigger rejects a direct rewrite of a restored reference. It requires zero missing, orphaned, checksum, provenance and authorization mismatches after repair. It verifies the database revision dynamically from the checkout.

**Existing volume compatibility: NOT VERIFIED.** The wrapper runs the same pinned server with `/data`, and the image expects UID/GID `10001`. That does not establish legacy `.minio.sys` metadata compatibility, permissions, encryption keys, bucket version or lifecycle state, multipart state, or downgrade safety. An operator must inventory the exact volume, MinIO release and ownership without writing; document encryption and key custody; quiesce writers for a coordinated database/object recovery point; create verified backups; exercise restore and the full application contract on separate volumes; review checksum and reference counts; approve a cutover and rollback window; retain the original volume offline and read-only. Never infer rollback safety from a container restart; restore to a separately verified compatible destination. No protected volume was attached.

## Credentials and monitoring

The API's `Settings` has empty S3 access/secret key defaults; local Compose has explicitly local-only boot credentials. The configured storage adapter signs requests server-side. Candidate delivery uses application authorization and backend Range; the browser is not given a bucket access/secret key. The rehearsal's root identity administers only generated fixtures. It issues short-lived STS credentials with distinct object prefixes and separate read/write rights and checks wrong-prefix reads/writes, unsigned requests and invalid credentials. The STS injection used by the rehearsal is via the adapter's client hook; production config does not currently expose a session-token field or prove per-tenant credential issuance. Application authorization and storage scope are separate controls. Repository review and synthetic rejection are not evidence about deployed secrets or tenant policies.

For an approved environment, use a private secret store and workload identity where supported. Split service read/write scope from bucket, recovery and credential administration. Review resource prefix and list scopes, require HTTPS with verified certificates, and keep Console access restricted to operators. Rotate by introducing a second narrowly scoped identity, verifying private playback, ingestion and restore, cutting clients over and revoking the old identity. Verify rejection after revocation; assign custody and emergency revocation to named operators. Do not reuse root keys or copy `.env` files into artifacts. **Production IAM, rotation and revocation: NOT VERIFIED.**

| Signal | Operator requirement |
| --- | --- |
| Guard unavailable or backend unhealthy | Probe guarded readiness and a synthetic signed read from the application network; distinguish connection failure from an unhealthy backend; page on consecutive failures. |
| Unsafe write denial or unexpected backend route | Count HTTP denial marker by service and status without URLs; use unprivileged IPv4/IPv6 black-box probes of both backend ports. Alert immediately on any reachable backend. |
| Unauthorized requests or repeated credential failures | Count status and bounded failure classes, alert on sustained deviations, and route investigation through restricted identity logs. Avoid request URLs, query strings, object keys or bodies. |
| Capacity, integrity and backups | Record bucket/volume usage, free bytes, checksum mismatch counts, age and status of last verified backup, and restore reconciliation counters. Page on integrity/restore failure or backup age exceeding the approved recovery objective. |

The rehearsal tests readiness, guard denials, reachability, credential rejection, integrity and recovery signals. Collection, capacity thresholds, paging, operator response and production logging are **PARTIAL**; no monitoring was deployed. Never log candidate recordings, source text, credentials, signed URLs, private keys, or request bodies. Use aggregate counts and synthetic canaries.
