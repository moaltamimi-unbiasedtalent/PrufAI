## GitHub Actions trust

The repository default token permissions were read-only and Actions approval of pull requests was disabled. Repository action selection allowed all actions and repository-level SHA pinning enforcement was disabled. Organization rules and deployment settings were unavailable. The workflow definitions independently grant only `contents: read`, disable Git credential persistence and pin all actions to commits already downloaded by the baseline run.

| Action | Full verified baseline commit |
| --- | --- |
| `actions/checkout` | `11d5960a326750d5838078e36cf38b85af677262` |
| `actions/setup-node` | `49933ea5288caeca8642d1e84afbd3f7d6820020` |
| `actions/setup-python` | `a26af69be951a213d495a4c3e4e4022e16d87065` |
| `actions/setup-go` | `40f1582b2485089dde7abd97c1529aa768e1baff` |
| `actions/upload-artifact` | `ea165f8d65b6e75b540449e92b4886f43607fa02` |

The workflow uses `pull_request`, ordinary push and manual dispatch. It has no privileged `pull_request_target` path, called reusable workflows, repository-secret inputs or OIDC grants. Pull-request code can execute package install and test scripts and use Docker on ephemeral hosted runners. The tests use disposable databases and synthetic credentials. The npm cache contains registry downloads scoped by the lock hash and GitHub's ref rules. Locked npm installs revalidate integrity. The Go cache action is disabled. Published evidence is generated by the checked-out code, so a reviewer should verify the producing workflow and revision before using a PR artifact as trusted provenance. Artifact retention is 30 days for O1A evidence. No production workflow consumes a PR artifact. [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use)

## Reading the evidence

The [separate workflow](../../../.github/workflows/supply-chain.yml) uploads a language bundle and a container/Go bundle. Select the run associated with the exact PR head. The evidence workflow explicitly checks out the PR head. The artifact name and `summary.json` identify that SHA. The separate application workflow uses GitHub's standard pull-request merge check.

- The language bundle contains CycloneDX SBOMs, package audit JSON, Python resolutions and `pip check` logs, npm lock hashes, the Next.js build tree hash and the first-party wheel hashes. The exact tool versions are in `language-toolchain.json`. `pip-audit` uses the public PyPI advisory feed. First-party wheels have no published registry advisory records.
- The container bundle records each Linux amd64 image's config ID, registry digest where applicable, layer hashes, Trivy vulnerability database timestamp, OS/language package inventories, CycloneDX SBOMs and raw advisory JSON. It also contains Go module build info, binary hashes and `govulncheck` binary findings. Go symbol evidence does not establish a reachable runtime call path. No claim is made for other architectures, OS packages outside the images or stripped binaries beyond scanner coverage.
- The evidence job pins Trivy `0.76.2` to the checksum in its [immutable release](https://github.com/aquasecurity/trivy/releases/tag/v0.76.2). Go module integrity is verified by the public Go checksum database. The separately installed `govulncheck` is `v1.9.0`, built using Go `1.26.10`. The scanned MinIO application builds continue to use Go `1.24.13`. [Trivy container coverage](https://trivy.dev/docs/latest/target/container_image/) · [Go vulnerability management](https://go.dev/doc/security/vuln/)
- `summary.json` lists each scanner finding separately, with the affected artifact, package, version, available fix, observed scope, owner role and initial disposition. If the feed omits a version range or severity, it stays unknown. Container counts are package/advisory occurrences per image, so a shared CVE can appear in several images. Go findings can overlap those counts. Incomplete targets report `NOT_VERIFIED` and fail collection. Findings are informational and visible. The existing production npm audit remains a blocking check.
